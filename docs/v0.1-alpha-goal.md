## 1. Purpose

This document records the next product target for vibit:

```text
short_term_release_target: v0.1_alpha
long_term_product_target: ai_era_nakama_pitaya_class_server_framework
```

The immediate goal is not another internal proof-only milestone. The immediate goal is a first alpha release that real developers can download, run, inspect, and use as the starting point for contribution.

The long-term target is to become an AI-era Pitaya or Nakama: a serious open-source game/backend server framework in the same product class, adapted around vibit's agent-native maintainability model.

## 2. Current Status

vibit is pre-alpha.

The repository is no longer only in a constitutional design phase. It now has a Go runtime, WebSocket + Protobuf request handling, PostgreSQL persistence boundaries, authentication/token/session service behavior, login and logout protocol routes, runtime session metadata, first-message connection binding, active connection lifecycle primitives, and a server-owned presence lifecycle snapshot.

The current continuation queue remains:

```text

```

The next time the maintainer asks to continue, agents should still use `.arch/work-items.yaml` and advance the next ready work item. This document changes the product destination, not the immediate continuation mechanism.

## 3. v0.1 Alpha Definition

`v0.1 alpha` is the first developer-usable release of vibit.

It should be a single-node, PostgreSQL-backed, WebSocket + Protobuf game backend runtime that external developers can run locally and use to validate vibit's agent-native server framework direction.

The release is successful when a technically capable developer can:

- clone the repository,
- read a short README that explains what vibit is,
- start or verify the runtime with documented prerequisites,
- understand the current WebSocket + Protobuf protocol surface,
- create or obtain a first player credential through a documented local flow,
- authenticate with a device credential,
- receive an opaque access token and runtime session metadata,
- send at least one protected gameplay request,
- observe a basic presence query,
- logout,
- run the repository checks,
- understand what remains intentionally out of scope,
- and find a concrete path to contribute the next slice.

## 4. Must-Have Alpha Capabilities

The alpha should include:

- README and runbook instructions that are accurate enough for a new developer.
- A PostgreSQL migration path for the runtime tables used by the alpha flow.
- Local verifier key configuration instructions that avoid committing secrets.
- A player onboarding path: create player account, issue first device credential, show raw credential once, and store only digests.
- Device credential login through the protocol route.
- Opaque access-token validation for protected gameplay routes.
- Runtime session creation and response session metadata.
- First-message WebSocket connection binding.
- At least one protected gameplay route, using the inventory proof slice.
- Presence lifecycle and a protected presence query over the server-owned snapshot.
- Logout route.
- A minimal example client, script, or documented request loop.
- Health, readiness, version, or configuration-check surface sufficient for local troubleshooting.
- A concise alpha acceptance checklist.

## 5. Preferred Near-Term Sequence

After this goal-setting slice, the recommended path is:

1. Complete `W-0178`: define and implement the protected presence protocol query functional slice.
2. Add a first local onboarding/device credential issuance flow.
3. Prove an authenticated gameplay end-to-end path: onboarding -> login -> connection binding -> protected inventory -> presence query -> logout.
4. Refresh the runtime runbook around actual authentication, sessions, migrations, and local config.
5. Add a minimal example client or request-loop script.
6. Add a health/readiness/version/config check surface.
7. Package the alpha developer flow and document prerequisites.
8. Add a `v0.1 alpha` acceptance check or equivalent checklist once the surface is stable.

This sequence may be adjusted by later ADRs, but future agents should prefer work that shortens the path to a runnable alpha over internal-only expansion.

## 6. v0.1 Alpha Non-Goals

The alpha does not need:

- Direct Nakama or Pitaya API compatibility.
- Distributed runtime, cluster mode, service discovery, or server-to-server RPC.
- Full chat, friends, groups, parties, leaderboards, tournaments, matchmaking, or match runtime.
- Full SDK matrix.
- Admin console or full operations dashboard.
- Production security hardening, SLA, or hosted deployment packaging.
- External identity providers, OAuth, OIDC, password login, or account recovery.
- Durable or distributed presence.

Non-goals do not mean these capabilities are unimportant. They mean the first alpha must stay narrow enough to finish.

## 7. Long-Term Product Target

The long-term target is:

```text
ai_era_nakama_pitaya_class_server_framework
```

This means vibit should become a serious open-source server framework in the same product class as Nakama and Pitaya, while keeping vibit's own design constraints:

- agent-native maintainability,
- explicit architecture manifests,
- contract-first behavior,
- generated repeatable structure,
- bounded change workflow,
- checkable repository state,
- strong transport/protocol/application/domain separation,
- and durable project memory through change specs, ADRs, and conversation logs.

Nakama remains the primary reference for broad game backend product coverage. Pitaya remains the primary reference for Go game server architecture vocabulary. vibit should match the class of useful capability, not accidentally copy public APIs, data models, route names, or clustering internals.
