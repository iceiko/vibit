## 3. v0.1 Alpha 定义

`v0.1 alpha` 是 vibit 的第一个 developer-usable release。

它应当是一个 single-node、PostgreSQL-backed、WebSocket + Protobuf game backend runtime，让外部开发者可以在本地运行，并验证 vibit 的 agent-native server framework 方向。

当一个具备技术能力的开发者能够完成以下事情时，这个 release 才算成功：

- clone 仓库；
- 通过简短 README 理解 vibit 是什么；
- 按文档准备 prerequisites 并启动或验证 runtime；
- 理解当前 WebSocket + Protobuf protocol surface；
- 通过文档化的本地流程创建或获得第一份 player credential；
- 使用 device credential 登录；
- 获得 opaque access token 和 runtime session metadata；
- 发送至少一个 protected gameplay request；
- 查询 basic presence；
- logout；
- 运行 repository checks；
- 理解哪些能力仍然有意不在范围内；
- 找到一个明确的下一步贡献入口。

## 4. Alpha 必备能力

Alpha 应包含：

- 对新开发者足够准确的 README 和 runbook instructions。
- Alpha flow 所用 runtime tables 的 PostgreSQL migration path。
- 不提交 secrets 的 local verifier key configuration instructions。
- Player onboarding path：创建 player account、签发 first device credential、raw credential 只展示一次、只存 digest。
- 通过 protocol route 的 device credential login。
- Protected gameplay routes 的 opaque access-token validation。
- Runtime session creation 和 response session metadata。
- First-message WebSocket connection binding。
- 至少一个 protected gameplay route，使用 inventory proof slice。
- Presence lifecycle，以及基于 server-owned snapshot 的 protected presence query。
- Logout route。
- 一个最小 example client、script 或 documented request loop。
- 足以支持本地 troubleshooting 的 health、readiness、version 或 configuration-check surface。
- 简洁的 alpha acceptance checklist。
- Packaged local alpha developer flow。
- Release publishing decision gate。
- Release execution preparation gate。
- Release execution authorization gate。

## 6. v0.1 Alpha 非目标

Alpha 不需要：

- Direct Nakama 或 Pitaya API compatibility。
- 在后续 ADR 重新激活 Pitaya 为 active architecture reference 前，加入 Pitaya-style distributed runtime、cluster mode、service discovery 或 server-to-server RPC。
- 完整 chat、friends、groups、parties、leaderboards、tournaments、matchmaking 或 match runtime。
- 完整 SDK matrix。
- Admin console 或完整 operations dashboard。
- Production security hardening、SLA 或 hosted deployment packaging。
- External identity providers、OAuth、OIDC、password login 或 account recovery。
- Durable 或 distributed presence。

非目标不表示这些能力不重要。它只表示第一版 alpha 必须窄到能完成。

## 7. 长期产品目标

长期目标是：

```text
ai_era_nakama_pitaya_class_server_framework
```

在 `ADR-0127` 之后，这表示 vibit 应成为与 Nakama 同一产品级别的严肃开源 server framework，同时把 Pitaya 暂缓到未来 distributed architecture review。核心产品承诺是 AI-native development 和 AI-native testing：用户说出需求，AI 负责从 spec 到 tests、implementation、verification 和 project memory 的结构化路径。

设计约束仍然是：

- agent-native maintainability；
- explicit architecture manifests；
- contract-first behavior；
- generated repeatable structure；
- bounded change workflow；
- checkable repository state；
- 强 transport/protocol/application/domain separation；
- 通过 change specs、ADRs 和 conversation logs 保存 durable project memory；
- requirement records；
- acceptance criteria；
- test plans；
- generated or updated tests；
- verification records。

Nakama 是 broad game backend product coverage 的主要参考。Pitaya 暂缓为未来 architecture planning。vibit 要匹配的是同级别可用能力，而不是意外复制 public APIs、data models、route names 或 clustering internals。

## 8. Agent 续接规则

未来 Codex session 直接在本仓库目录中启动时：

1. 阅读 `AGENTS.md`、`.arch/work-items.yaml` 和本文。
2. 运行：

```bash
node tools/vibit inspect next
node tools/vibit check work --json
```

3. 如果维护者说 `继续推进` 或 `continue`，推进 exactly one next-ready work item，除非遇到 ask-first boundary 或 verification failure。
4. 把 `v0.1 alpha` 作为短期 release target。
5. 把 AI-era Nakama-first capability 和 AI-native requirement/test/implementation workflow 作为长期目标。
6. 优先使用 `ADR-0082` gate-density rules：security-critical work 保持明确 gate；普通 functional work 用一个 bounded slice，并把 boundary 嵌入 change spec；轻量 docs/tooling 在简单时可以 direct。
7. 每个 verified continuation slice 都要及时 commit 和 push。
